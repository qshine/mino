# Mino 逐章实现草案

本目录根据[英文路线图](../books/en/plan-todo-chapters.md)设计，供每章开始前二次讨论。第 01 章记录已经实现的基线；第 02–09 章均为**待讨论草案，尚未实现**。文中的文件名、接口、命令、数据格式和限额是建议方案，不表示已经存在或已经批准。

设计基线：`c4d6ac3`，Go 1.27.1，OpenAI Go SDK v3.66.0。后续开章时应先核对当时的代码和 SDK，再更新本章草案。目标版本只表示章节归属，不提前创建标签。

这些中文文档面向实现讨论，不属于双语教程正文。VitePress 的 `srcDir` 是 `docs/books`，所以 `docs/plans` 不进入在线书籍导航和构建；提交到公开仓库后，文件仍然公开可见，不可包含私人记录。

## 贯穿各章的实现约定

1. **三个层次分开。** JSONL 是本地事实记录；内存状态是记录的恢复结果；请求上下文是按规则选出的内容。文件里有某条记录，不代表模型每次都能看到它。
2. **一个用户回合有明确结束点。** 从一条用户输入开始，包含零次或多次工具步骤，直到最终回答、失败或取消。只有收到完整的 Responses 完成事件，才能把对应模型响应作为完成结果保存。
3. **先保证记录可写，再产生外部效果。** 用户输入先持久化再请求模型；工具开始记录先持久化再执行。写入失败后停止继续推进，不宣称已经保存，也不自动重试可能产生副作用的操作。
4. **历史不等于授权。** 历史里的用户文字、工具输出、摘要、Skill 和 MCP 描述都不能充当可以再次使用的执行许可。授权绑定当前操作、参数、目标和运行环境，由程序检查。
5. **保留协议关联。** 从第 03 章起，模型输出项和工具结果按原顺序回放，保留 `call_id`；不能把结构化调用简化成一段聊天文本。具体 SDK 转换方式在该章开工时验证。
6. **安全控制随功能出现。** 第 02 章处理私有文件和写入故障；第 03 章有逐次批准和执行限额；第 07、08 章限制外部内容与服务。第 09 章统一已有规则，不补交前面缺失的基本控制。
7. **逐步提取代码。** 延续 `internal/` 下的 `mino` 包；先用具体类型和短函数。仅在多个工具或实现真正需要替换时提取小接口，不预建插件框架、通用事件总线或数据库层。
8. **保留现有运行约定。** 仅支持 Responses API；沿用 `~/.mino/config.json`、启动时读取一次的 `~/.mino/SOUL.md`、英文提示和错误。不读取项目配置、项目 `AGENTS.md` / `SOUL.md` 或 `OPENAI_*` 变量作为运行配置。

## 跨章数据演进

| 首次引入 | 持久化内容 | 请求上下文如何使用 | 下一章必须保留的性质 |
| --- | --- | --- | --- |
| 02 | 用户消息、完成的回答、回合结束状态 | 回放成功完成的回合，再加入当前输入 | 顺序、版本、尾部恢复和单写入者 |
| 03 | 完整模型输出项、工具开始和结果 | 加入关联完整的模型输出与工具结果 | 已执行操作不能因重启而重放执行 |
| 04 | 每个会话独立日志，活动会话指针 | 只读取当前会话 | ID、锁和清空操作的隔离 |
| 05 | 摘要检查点及其覆盖范围 | 摘要加保留的最近回合 | 原文仍在；摘要不提升来源权限 |
| 06 | 无需保存每次估算值 | 对最终组装的请求做预算 | 同一组装路径用于估算和发送 |
| 07 | Skill 读取作为普通工具调用和结果 | 启动目录摘要加实际读取的内容 | 来源可辨认，完整正文按需进入 |
| 08 | MCP 调用及适合回放的结果 | 复用工具协议与预算 | 命名、服务来源、错误类型稳定 |
| 09 | 最小必要的决策记录，不保存许可凭证 | 来源信息可读，权限由代码决定 | 策略更新后，旧历史不能绕过新规则 |

JSONL 的字段按章扩展。早期代码遇到不支持的版本或记录类型应停止并说明原因，不默默忽略后继续追加；新版本负责读取自己承诺兼容的旧格式。不要在第 02 章一次性实现本表后面所有记录。

## 每章开始前的二次讨论

各章末尾列出具体待定问题。讨论时优先确认：

- 本章演示的一个完整交互、明确不做的内容，以及能否删减非必要功能。
- 失败、取消、重启和数据迁移后的可见行为；涉及数据删除时的确认方式。
- 建议字段、命令、限额与上一章实际实现是否一致；新增依赖是否确有必要。
- 哪些验收由模拟服务确定验证，哪些只是依赖模型行为的演示。

讨论结果直接更新对应文件，将状态改为“已讨论，待实现”，并记下日期与决定。开发后再把建议文件名和接口替换成实际位置；未达成一致的问题保留。路线图负责能力状态，本目录负责实现决策，不用草案改变路线图中的“尚未开始”。

## 实现与交付检查

每章计划中的任务按顺序执行；任务表的测试描述是待编写的测试，不代表仓库已有这些测试。一般每完成两项任务检查一次端到端交互。现有统一验证命令从仓库根目录运行：

```bash
go test ./...
bash scripts/check.sh
npm run book:build
```

测试使用 Go 标准测试工具、临时 HOME、临时历史文件和本地模拟 Responses / MCP 服务。默认不连接真实模型、不使用真实密钥，也不执行面向真实用户文件的破坏性操作。逐章测试侧重可观察行为和失败恢复，不追求与实现逐行对应的测试。

代码和相关检查完成后，按 [AGENTS.md](../../AGENTS.md) 调用 `book_writer` 更新中英文教程，再由主代理核对事实、翻译和书籍构建。各章至少补充一条正常交互和一条失败交互；README、SOUL 的默认能力说明、配置指南和 CHANGELOG 按实际影响更新。保留已存在的用户 SOUL，不自动覆盖。

提交保持聚焦；实际发版时使用新的 `0.<chapter>.<patch>` 版本，不改写已发布标签或资源。方案编写本身不执行章节代码、迁移本地数据或创建发布。
