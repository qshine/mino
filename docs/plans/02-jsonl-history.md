# 第 02 章：JSONL 对话历史

状态：**已实现并通过验收**（2026-09-24）。对应版本：`v0.2.0`。前置：[第 01 章](./01-terminal-chat.md)。下文保留设计与验收约定，公共约定见[计划索引](./README.md)。

## 1. 本章交付

让一条连续对话在重启后仍可接着聊。用户先说 `Remember the word pine.`，退出后再问 `What word did I give you?`；模拟服务应在第二次请求中看到上一回合和当前问题，终端仍实时显示回答。

本章只维护一份 `~/.mino/history.jsonl`，不增加多会话、工具、摘要或自动截断。`store: false` 保留；上下文由本地记录显式构造，不依赖服务端会话 ID。

## 2. 数据与文件

使用小型 `historyRecord` 类型：`v` 为格式版本，`seq` 为文件内递增序号，`turn_id` 关联一次用户回合，`kind` 区分记录，消息带 `text`，结束记录带 `status`。回答记录还可带 `output`，保留完成响应的 message/reasoning 输出项（包括 phase 与 encrypted_content），按官方手动上下文指南原样回放；本章不执行工具。无 output 的兼容服务以已完成的文本回答回放。不保存 API 密钥、HTTP headers 或原始错误响应。

示意文件，三行分别是三个有效 JSON 对象：

```jsonl
{"v":1,"seq":1,"turn_id":"t1","kind":"user_message","text":"Remember the word pine."}
{"v":1,"seq":2,"turn_id":"t1","kind":"assistant_message","text":"The word is pine."}
{"v":1,"seq":3,"turn_id":"t1","kind":"turn_end","status":"completed"}
```

一份 JSONL 文件对应一个会话，记录中不保存 `session_id`。`turn_id` 使用程序生成的 32 位随机十六进制标识，关联一轮问答，示例缩写只便于阅读。`turn_end` 的状态为 `completed`、`failed`、`cancelled`、`interrupted`；只有 `completed` 的成对消息进入后续上下文。失败输入仍在本地日志，用户可重新输入，程序不自动重发。

- 父目录使用已有 `userDirectory()`；日志和锁文件 `0600`，拒绝非普通文件和符号链接。锁文件保持固定，不通过删除锁文件释放锁。
- 从打开到关闭持有本机进程级排他文件锁。第二个进程明确提示历史正在使用，不允许两个写入者交错追加；锁由进程关闭自动释放。
- 每条记录先在内存编码为一行再追加。单次写入不被当作事务保证，检查短写、编码和 `Sync` 错误。成功边界需同步到文件后才更新可提交的内存视图。
- 初始上限为每条记录 16 MiB、整个历史 64 MiB；达到限制就停止追加并说明原因，不悄悄丢弃旧消息。它们是内存/磁盘防护，不是 token 预算。
- `seq`、回合顺序、版本和类型都必须校验。未来类型不能被旧程序静默跳过。

## 3. 请求、显示与提交

在 `internal/conversation.go` 中实现具体的对话控制器，在 `internal/history.go` 实现读写。最初无需通用存储接口。客户端改为接收有序消息集合，回调显示增量，并返回一个只有成功完成时才有效的回答结果。

一次输入按以下顺序处理：

1. 验证输入和日志可写；追加并同步 `user_message`。失败则不发送模型请求。
2. 从成功回合构造此前的消息列表，再加当前输入。每次请求重新提供已加载的 SOUL，不把身份文本重复写进聊天日志。
3. 发送请求，边接收边显示，同时在客户端收集原始回答文本。保留现有响应总量限制；显示过滤不改写保存的语义文本。
4. 收到成功完成事件后追加 `assistant_message` 和 `turn_end: completed`，同步成功后把该回合纳入下一次上下文。
5. 请求失败或取消时记录相应 `turn_end`。终端已经显示的增量不写成成功回答，也不参与后续上下文。拒绝但完整结束的回答可以正常保存。
6. 如果回答已经显示但持久化失败，明确提示 `Answer displayed, but saving history could not be confirmed:`，停止本次聊天，避免内存与文件继续分叉。不能继续显示“已保存”。

模型失败本身可允许下一问；历史写入失败则不可继续。停止期间若不能写入结束记录，交给启动恢复流程判断。

## 4. 启动恢复与故障规则

按文件顺序逐行扫描，记录最后一条完整有效记录的字节偏移。以换行符作为记录提交边界：没有结尾换行的尾部字节即使能解析成 JSON，也不视作已提交。

| 情况 | 建议行为 |
| --- | --- |
| 日志不存在或为空 | 创建私有空文件，开始第一回合 |
| 最后一行无换行或是损坏 JSON，之前全有效 | 先把原文件保存到私有恢复副本并同步，再截去该尾部、同步修复文件；任一步失败就停止。告知恢复结果，避免静默吞记录 |
| 中间行损坏、序号倒退、未知类型/版本 | 停止启动，给出行号和修复指引；不跳过后继续聊天 |
| 尾部是完整 JSON，但违反字段或回合约束 | 停止并保留文件，不能把语义错误误当作可丢弃的尾部残片 |
| 用户消息之后没有 `turn_end` | 保留已提交记录，追加 `interrupted`；该回合不进入上下文，也不自动请求模型 |
| 有回答记录但没有完成结束记录 | 同样视作中断，不推测最后一次同步是否成功 |
| 第二个进程占用历史 | 拒绝写入，退出并给出英文提示 |

恢复副本会保留私人对话，权限与主文件相同；只在确有损坏时创建，并告诉用户位置。普通退出不复制整个历史。此方案只保证单机文件语义，不声称在所有文件系统或断电情形下实现数据库事务。

每行是一项实现任务，预计涉及 2–5 个文件；“测试”指该任务需要新增或调整的行为测试。

| 任务 | 依赖 | 建议文件 | 验收与验证 |

| 02-B：接入一份 JSONL | A | `history.go`、`history_test.go`、`conversation.go`、`app.go` | 临时 HOME 中写入、退出、重启后恢复；完整配置和 SOUL 不变；用户记录写失败时 HTTP 请求数为零 |

## 6. 教程与下一章的衔接

教程以“重启后仍能提起 pine”为例，展示磁盘记录、内存消息、实际请求三者。明确本章默认回放全部成功历史，最终可能超过服务的上下文限制；暂时报错，不声称已经有自动管理。

第 03 章会扩展记录类型保存结构化模型输出和工具结果，不能只扩展 `text` 字段模拟工具。它也会重新定义产生过工具效果的失败回合如何进入上下文；本章的“只回放完成回合”仅适用于尚无工具的阶段。

## 8. 本次实现决定

- 一份 JSONL 文件对应一个会话，记录不保存 `session_id`；第四章用 `sessions/<session_id>.jsonl` 的文件名标识会话。
- 用户输入先保存；仅成功完成的回合进入上下文，不完整回答仅留在终端。
- 损坏尾部先备份再修复；中间损坏或语义错误停止启动。
- 单条记录 16 MiB、整文件 64 MiB；到限停止，不自动删除或压缩。
- 排他锁面向本机 macOS 文件系统，不承诺多主机共享目录并发安全。
- 代码检查后已由 book_writer 更新教程，主代理完成双语内容和图示复核。

旧的未发布开发格式若含顶层 `session_id`，会被未知字段校验拒绝，原文件保持不变。退出程序并创建私有备份后，可仅移除每条记录的该顶层字段，保留正文、其他字段和换行，再重新加载；也可保留备份并移开旧文件重新开始。
