# 第 02 章：让对话连续起来——JSONL 对话历史

适用版本：**0.2.x** · 源码版本：**[v0.2.0](https://github.com/qshine/mino/tree/v0.2.0)**

告诉 Mino「我最喜欢的颜色是蓝色」，然后退出。再打开程序，问它刚才说的是什么颜色。这次，多了一道坎，连刚才那个进程都没了，前文从哪里来？这一章，我们把那句蓝色留到文件里，再跟着它回到下一次请求。

请使用 `v0.2.0` 源码，前置条件及安装方法见[准备与安装](../getting-started.md)。你会接触对话历史，也会遇到一个容易忽略的问题，已经显示在屏幕上的话，到底什么时候才算存好了。

## 1. 关掉程序，再问一次颜色

在 `v0.2.0` 的仓库根目录启动 Mino，先交给它一条很容易核对的信息。

```bash
go run ./cmd/mino
```

交互示意，下面展示操作过程，并非真实 API 调用记录。

```text
Mino - Chapter 02: Conversation History
History is saved locally and restored on startup. Use /exit, Ctrl+D, or Ctrl+C to quit.

You> 我最喜欢的颜色是蓝色。

Assistant> 你最喜欢的颜色是蓝色。

You> /exit
```

再运行同一条命令，输入「我刚才说最喜欢什么颜色？」。

先别急着看模型怎么答。Mino 启动时就会恢复对话，旧聊天记录不会在终端重新滚一遍，也不会因为重启就向模型发请求。等你提交新问题，前面的问答才和它一起送出去。模型这次有了可以参考的前文，具体措辞仍由服务决定。

那句蓝色，重新进入了请求。

同一次运行里继续追问，也走这套流程。你想想看，文件躺在 Mac 上时，模型服务并不能直接看到它。Mino 还得把里面合适的内容取出来，交给模型。这一步接上了，聊天才接得上。

## 2. 给这段对话留一本账

回到文件这块。Mino 把当前这段对话保存在 `~/.mino/history.jsonl`，重启时重新打开它。一段有归属的对话叫会话；一轮问答从提交问题开始，顺利完成时，以完整回答结束。当前只有这一个会话文件。

JSON Lines（JSONL）的做法很直观，一行放一条 JSON 记录。新记录往后追加，Mino 不用每问一句，就把之前的聊天全部重写一遍。

说到这里，很容易想，记下问题，再记下回答，不就够了吗？

还差一句，这一轮完成了。

表 02-1：颜色问答会留下三条记录，结束记录决定它能否进入后文。

| 记录类型 | Mino 何时保存 | 留下的依据 |
| --- | --- | --- |
| `user_message` | 发出请求之前 | 这一轮已经提交了什么问题。 |
| `assistant_message` | 模型成功完成生成后 | 完整回答文本，以及返回的响应输出项。 |
| `turn_end`，`status: completed` | 和回答记录一起保存 | 这一轮成功结束，保存确认后可以加入后续上下文。 |

这三条记录靠 `turn_id` 配成一轮。每一轮使用新的 ID，由 32 个小写十六进制字符组成。同一轮共用它，下一轮不能拿来继续用。文件中的 `seq` 从 1 开始连续递增，每条记录还带着格式版本 `v: 1`。加载时，Mino 会检查这些字段和问答顺序，防止把一个问题配上另一个问题的回答。

这里不用再塞一个会话 ID，记录所在的文件已经说明它属于哪段对话。规划中的第 04 章才会把多个会话分别放到 `~/.mino/sessions/<session_id>.jsonl`，让 `/new` 创建新文件，文件名承担会话标识。

如果这些字段第一次看有点绕，先抓住颜色这个例子就行。同一轮的三条记录要对得上，结尾还要确实完成。后面恢复聊天，靠的就是这份依据。

## 3. 文件里的蓝色，怎样回到模型面前

先把两个容易混在一起的词拆开。对话历史是磁盘上保存的记录，上下文是模型这次生成时实际收到的信息。Mino 从历史里按顺序还原已完成的问答，在内存中准备好，再接上你当前的问题，组成请求的 `input`。

这回，「我刚才说最喜欢什么颜色？」前面，终于有了那句蓝色和对应的回答。

从 `~/.mino/SOUL.md` 加载的指令仍单独发送。Mino 也继续设置 `store: false`，逐次显式提供前文，不借助 `previous_response_id` 或服务端管理的 `conversation` 接续对话。

不过，能接上还不够。程序得知道，哪一刻才能放心接受下一句。

```mermaid
sequenceDiagram
    accTitle: 恢复对话并保存完整的一轮问答
    accDescr: Mino 启动时从本地 JSONL 历史加载已完成的问答，先保存当前输入，再请求模型并显示回答片段，最后保存完整回答及结束记录，才将本轮加入上下文并接受下一个问题。
    actor User as 读者
    participant Mino as Mino
    participant API as 模型服务
    participant Disk as 本地 JSONL 历史
    Mino->>Disk: 启动时加载并校验记录
    Disk-->>Mino: 这个文件中已完成的问答
    User->>Mino: 当前问题
    Mino->>Disk: 追加输入并同步文件
    Disk-->>Mino: 输入已保存
    Mino->>API: 已完成的历史与当前问题<br/>已加载的指令
    loop 回答片段陆续到达
        API-->>Mino: 新增文本片段
        Mino-->>User: 显示片段
    end
    API-->>Mino: 成功完成与响应输出项
    Mino->>Disk: 追加回答及 completed 结束记录，再同步文件
    Disk-->>Mino: 本轮已保存
    Mino->>Mino: 将已完成的本轮问答加入内存上下文
    Mino-->>User: You>
```

图 02-1：回答可以先显示，下一句要等这一轮完整保存后才能开始。

小屏幕上可以横向滚动图表。沿着图里的箭头走，会遇到[两次存储确认](https://github.com/qshine/mino/blob/v0.2.0/internal/conversation.go#L90)。请求模型前，输入先写入并同步；再次显示 `You>` 前，回答和结束记录也要写入并同步。任何一次写入或同步失败，聊天都会停下来。

再往里看一层，保存回答也不只是抄下屏幕上的字。`text` 留下回答文本，可选的 `output` 留下结构化响应项。Mino 保留返回的助手消息项，包括 `phase`，也保留带有不透明 `encrypted_content` 的推理项，并通过 `include: ["reasoning.encrypted_content"]` 请求这份状态。下次请求时，服务还能收到继续处理所需的信息，Mino 自己不会显示或解密它。

兼容服务如果在完成时没有返回输出项，Mino 会用成功完成的流式文本构造助手消息。至于终端上的 `Assistant>`，那是程序打印的标签，不会混进回答里。

我觉得这一层挺值得停一下。我们在屏幕上读到的回答，只是这次交互的一部分；要把交互继续下去，程序还得保留服务返回的相关状态。

## 4. 半句话，可以留下痕迹，但不能算完成

说真的，如果只是正常退出再打开，记历史看起来不算难。难处在那些没走完的时刻，网络断了、你按了取消，或者程序还没存完就停了。

先看请求失败。输入已经保存，Mino 会追加一个状态为 `failed` 的 `turn_end`；取消则记录为 `cancelled`。这两种问答都不会进入后续上下文。你已经看到的片段会留在终端，却不会被保存成完整回答。普通请求错误之后还能继续提问，Ctrl+C 则取消并退出。

拒绝回答又是另一回事。只要模型成功完成了拒绝，它就是一份完整回答。Mino 显示 `Model refused: `，保存时只留下模型的拒绝文本和返回的输出项，不把程序加的前缀塞进下一次请求。

再看更突然的中断。结束记录还没保存，进程就停止了，下次启动时，Mino 会把未结束的这一轮标成 `interrupted`，排除在上下文之外。恢复不会自动重发请求。

这块还有一道边界。如果文件最后一行没写完整，或者最后一行 JSON 语法损坏，Mino 先留下私有恢复副本，再移除这段尾部。文件中间的无效记录、未知字段或版本，以及不合法的轮次 ID 或记录顺序，都不能这样带过去。程序会停止加载，历史内容保持不变。

顺着这个过程，你就能理解那个看起来有点扫兴的决定了。回答已经出来了，保存失败，为什么还要停止聊天？

因为接着聊下去，下一问可能依赖一段重启后根本恢复不出来的前文。**屏幕上看到了，和磁盘上存好了，是两次确认。** 保存输入失败时更早，Mino 会在请求模型之前停下。

完整的来回，才接进下一轮。

## 5. 别只看它答对蓝色，要看蓝色怎么过去的

坦率地讲，模型答了一句蓝色，我也不能只凭这两个字就认定恢复成功。它可能猜对。要把这一章跑明白，还是得检查第二次请求带了什么。

在包含第 02 章实现的仓库根目录运行下面的命令。

```bash
go test ./internal -run 'TestRunRestoresConversationHistory|TestRunFailedTurnDoesNotEnterContext|TestConversation|TestHistory|TestRunStreamsBeforeResponseCompletes'
```

这些测试使用临时用户目录和本机模拟 HTTP 服务，不读取你的真实历史，也不调用付费模型。通过时，`github.com/qshine/mino/internal` 前会显示 `ok`；测试进程需要能够绑定本机端口。

[重启检查](https://github.com/qshine/mino/blob/v0.2.0/internal/conversation_test.go#L17)就沿着开头那次颜色问答走。提交颜色，关闭 Mino，重新启动，再追问。测试直接查看第二次请求，确认原始输入、返回的推理与回答项，以及新问题都在其中。

还会再核对文件。两轮共六条记录，`seq` 连续，没有 `session_id` 字段；每轮内部共用有效的 `turn_id`，两轮之间用不同的 ID。到这一步，蓝色从哪里保存、怎样恢复、怎样发出，就都能对上了。

其他检查继续往不顺利的地方走，在示例问答的每个字节边界截断写入，模拟写入或同步失败，再尝试让第二个进程打开同一份历史。它们确认未完成问答不会进入上下文、存储失败会阻止后续请求，同一份历史也只能由一个进程使用。流式检查则守住第一章的体验，文字仍然先于完成事件显示。

## 6. 本章小结与下一步

关掉程序，那句蓝色也有了回来的一条路。Mino 保存完整问答，重启时恢复，再把前文交给模型。你可以重新做一次开头的实验，把注意力从回答对不对，移到这一来一回的信息有没有接上。

目前每次都会重放全部已完成的历史，对话越长，越可能碰到模型的上下文限制。上下文压缩、上下文预算，以及管理不同会话的 `/new` 和 `/clear` 都还在规划中。

我们能把话接下去了，模型请求一个动作时，Mino 还不会执行。规划中的第 03 章会补上这次交接，模型提出工具调用，程序决定是否执行，再把工具结果交回模型。后面的路见[章节规划](../plan-todo-chapters.md)。
