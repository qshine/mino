# Mino Chapter Roadmap

This tutorial builds a terminal agent from scratch in Go using the OpenAI Responses API. The official OpenAI Go SDK handles API communication; Mino implements the interaction flow and, in later chapters, the Agent loop. Each chapter follows one interaction: what the model receives, what the program does with the response, and how control or context reaches the next step. [Getting started](./getting-started.md) covers installation and API settings.

Chapter 01 has working code, a lesson, and local verification for the reissued `v0.1.0`, with its entry point in `cmd/mino` and application in `internal/mino`. The remaining chapters have not started. Statuses are **Not started**, **In progress**, and **Complete**. A chapter is complete only when its lesson, corresponding implementation, and necessary verification are all finished.

| Chapter | Status | Title | What it covers |
| --- | --- | --- | --- |
| 01 | Complete | [Your First Terminal Conversation](chapters/01-terminal-chat.md) | Trace current input and optional `AGENTS.md` instructions into a Responses request, extract the assistant reply, and return to the input prompt. Observe errors and cancellation, then use two questions and mock tests to show why independent requests have no memory. This is the foundation for an agent; history and model tool execution are not implemented yet. |
| 02 | Not started | Keeping a Conversation Going: In-Memory History | Keep exchanges in memory and include earlier context in each request for multi-turn conversations. History disappears when the process exits. Understand that model context comes from information the program supplies, and distinguish independent questions from a continuous conversation. |
| 03 | Not started | The First Agent Loop: Tool Calls and Bash | Register a Bash tool through `tools`, including its name, description, and parameter schema. Implement the cycle: model requests a tool, Go executes it, the result returns to the model, and the model calls another tool or answers. Preserve the association between tool calls and results and show execution progress. Introduce confirmation before execution, timeouts, output limits, and a maximum loop count alongside this capability. |
| 04 | Not started | Saving and Managing Conversations: SQLite and Sessions | Store sessions, conversation entries, and tool calls in SQLite so they survive restarts. Use `/new` to create a session while retaining the previous one, and `/clear` to remove the current session's history and summaries introduced by later chapters. Distinguish persisted records from the context actually sent to the model. |
| 05 | Not started | Manual Context Compaction: `/compact` | Summarize earlier exchanges while retaining recent exchanges in full and preserving original history records. Include the user's goal, constraints, completed work, and remaining work in the summary. Keep tool calls paired with their results, preserve the original context if compaction fails, and demonstrate information preserved or lost through summarization. |
| 06 | Not started | Automatic Context Management: Budgets and Triggers | Establish a context budget that accounts for system instructions, tool definitions, history, and tool results, while reserving room for model output. Automatically reuse compaction near the threshold. Handle oversized individual inputs or tool results, failed compaction, and context that remains too large after compaction. |
| 07 | Not started | Skills: Load Task Knowledge When Needed | Discover skills in the project's `.agents/skills/` and the user's `~/.agents/skills/`. At startup and on `/new`, include skill names, descriptions, and paths in instructions. After selecting a skill, the model uses a tool to read its complete `SKILL.md`. Explain discovery and on-demand loading without inserting every skill's full contents into every request. |
| 08 | Not started | MCP: Connect External Tools | Connect Go to MCP services, discover tool names, descriptions, and parameter schemas, and convert them into Responses API tool definitions. Forward calls to the corresponding service and return results to the model. Reuse the existing agent loop and handle naming conflicts, connection failures, and tool errors. |
| 09 | Not started | Guardrails: Keep the Agent Within Its Authorization | **Context controls:** explain jailbreaks and prompt injection; distinguish trusted instructions from external file, tool, and MCP content; preserve sources and trust boundaries during summarization. **Execution controls:** check concrete operations and arguments in code, then allow, reject, or request authorization; dangerous operations such as deletion require authorization bound to what will actually run. **Data access controls:** constrain where files and data can be read, written, or deleted; protect sensitive information and check path escapes and symbolic links. Explain the bypass risks of a general Bash tool and the roles of operating-system permissions and sandboxes. Verify behavior with injection attempts, denied authorization, and out-of-bounds access. |

Basic protections arrive alongside the capabilities that need them. Chapter 09 brings those controls together into a consistent permissions policy. Prompts and injection detection can reduce risk, but the program and execution environment must enforce actual permissions. Checking only command keywords such as `rm` is not a sufficient policy.
